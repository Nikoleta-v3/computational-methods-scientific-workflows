## 04 Documentation and project organisation

A research repository goes hand in hand with a research paper. It should help
your readers understand how the results were produced and how they can be
reproduced.

The structure of a research repository is often different from that of a
software package. This does not mean that a research project cannot produce a
software package. Rather, the primary goal of a research repository is to make
the code accessible and explain how readers can reproduce the results—for
example, how to run the simulations and generate the figures.

* GitHub should not be used as an unstructured archive where files are simply
    uploaded without any explanation of how to run the code.
* GitHub is useful for storing code, documentation, instructions, and
    supporting collaboration.
* If the goal is long-term archiving, use an archiving service such as Zenodo
    instead.
* Large datasets should also be archived or deposited in an appropriate data
    repository. The GitHub README should explain where the data are archived,
    what needs to be downloaded, and where the files should be placed within the
    project.

## Example: A research project repository

The repository <https://github.com/Axelrod-Python/revisiting-axelrod-second> is
an example of an academic project repository.

A useful README for this kind of project tells readers:

- what the project is about
- who collaborated on it
- where the simulation or analysis code lives
- how to install dependencies or run the code
- where generated data should be placed
- where archived data are available, for example on Zenodo
- which notebooks generate manuscript figures and supporting analyses
- where to find the associated paper or preprint

This is the kind of information a research repository needs. A reader should
not have to guess how code, data, figures, and the paper are connected.

## A suitable structure for the running example

For the running workshop example, a useful structure might look like this:

```text
computational_methods_workshop/
+-- README.md
+-- LICENSE
+-- .gitignore
+-- src/
|   +-- compute.py
+-- scripts/
|   +-- run_experiment.py
+-- notebooks/
|   +-- Fig1_analysis.ipynb
+-- data/
|   +-- README.md
+-- figures/
|   +-- README.md
```

The exact folders will depend on the project. The important point is that the
structure should make the workflow visible.

## README

The `README.md` is the front door of the project. It should explain enough for a
new reader to understand what the repository contains and how to begin.

For the running example, the README might start like this:

```markdown
# Computational Methods Workshop Example

This repository contains code for the running example used in the
Computational Methods for Scientific Workflows workshop.
```

## How to run the code

A research repository should tell people how to reproduce the main computation.

For the running example, the README could include:

~~~markdown
## Running the code

Install the required Python packages:

```shell
pip install pandas matplotlib dask
```

Run the example computation:

```shell
python src/compute.py 1000000
```

The script prints the computed value and the runtime.
~~~

If the project has several scripts, explain the order in which they should be
run. If a script takes a long time, say so. If it needs a specific input file,
name that file.

## Data

GitHub is not a good place for large datasets. It is also not the right place
for long-term data archiving.

For an academic project, the README should clearly state:

- which data files are generated by the code
- which data files must be downloaded separately
- where archived data are stored
- where downloaded data should be placed locally

For example:

~~~markdown
## Data

The scripts generate output data in the `results/` folder.

The archived simulation data used for the paper are available on Zenodo:

<ADD-ZENODO-LINK-HERE>

After downloading the archive, unzip it into:

```text
data/
```
~~~

If the data cannot be public, explain who to contact or what restrictions apply.

## Analysis and figures

Many academic projects have scripts or notebooks that turn data into figures,
tables, and supporting analyses.

Use folder names that tell readers what each part does:

- `notebooks/` for exploratory or figure-generating notebooks
- `scripts/` for repeatable command-line scripts
- `figures/` for generated figure files

If notebooks generate manuscript figures, name them clearly:

```text
notebooks/
+-- Fig1_analysis.ipynb
+-- Fig2_model_comparison.ipynb
+-- Appendix_A_sensitivity_analysis.ipynb
```

You do not need to explain every notebook in the main README. If there are many
notebooks, add a `README.md` inside the `notebooks/` folder.

For example:

```markdown
# Notebooks

Notebooks labeled `Fig` generate figures used in the manuscript.
Notebooks labeled `Appendix` contain supporting analyses.
```

## Paper and citation

If the repository was used for a paper, point to the paper.

The link should go both ways. The repository should point to the paper, and the
paper should point back to the repository and any archived data.

## License

A repository should include a license if other people are allowed to reuse the
code or materials.

Without a license, others should not assume that they can reuse the work. Which
license you choose depends on the project. You should also check whether your
institution or funder has a preferred license.

For the running example, add a `LICENSE` file and mention it in the README:

```markdown
## License

Code in this repository is released under the MIT License. See `LICENSE` for
details.
```

## Update the running example

Update the running example so that it has an academic project structure.

1. Update `README.md` with a short project description.
2. Add instructions for running the code.
3. Add a sentence about the license.

This is intentionally a simple example. By the end of the workshop, however, you
will have built a much more realistic research project. You can always come back
to this page as a reminder of how to structure an academic research repository.
