## 03: Scientific writing with LaTeX

Scientific writing is easier to maintain when the document is treated as part
of the research workflow. The manuscript, figures, tables, references, and code
should be organised so that another person can understand how the final output
was produced.

LaTeX is useful for this because it keeps the document in plain text. That
makes it easier to track changes with git, review edits, reuse figures and
tables, and manage references.

In this section, we will create a small LaTeX document with sections, a figure,
a generated table, and references.

## Why not only use Overleaf?

Overleaf is useful for collaboration, especially when co-authors are not
comfortable working locally. It is often the easiest way to share a draft.

However, for computational research, it is useful to understand a local LaTeX
workflow too.

A local workflow makes it easier to:

- keep the manuscript in the same repository as the analysis code
- track changes with git
- include generated figures and tables directly from project folders
- work offline
- compile the same document in a reproducible environment
- review changes through GitHub pull requests

The point is not that Overleaf is wrong. The point is that the writing process
should connect cleanly to the rest of the project.

## Recommended setup

For this workshop, we will use:

- VS Code as the editor
- the LaTeX Workshop extension for compiling and previewing documents
- a local LaTeX distribution for building PDF files
- git for tracking changes

Create a folder for the paper:

```shell
mkdir -p paper
```

Create a file called `paper/main.tex`.

## Create the first document

Add the following:

```latex
\documentclass[11pt]{article}

\usepackage{graphicx}
\usepackage{booktabs}
\usepackage{hyperref}

\title{A Short Example Paper}
\author{Your Name}
\date{\today}

\begin{document}

\maketitle

\section{Introduction}

This document shows how a short scientific manuscript can be written in
\LaTeX{} and connected to figures, tables, and references generated elsewhere
in the project.

\section{Methods}

The analysis was performed using scripts stored in the project repository.
Figures and tables were generated from the same data analysis workflow.

\section{Results}

The results section should refer to figures and tables using labels rather than
manual numbering.

\section{Discussion}

The discussion explains the main result, its limitations, and what should be
done next.

\end{document}
```

Compile the document from inside the `paper` folder:

```shell
cd paper
pdflatex main.tex
```

If you are using VS Code with LaTeX Workshop, you can also compile from inside
the editor. The important point is that the paths in the document should match
where the document is compiled from.

## Track the document with git

Because LaTeX files are plain text, they work well with git.

After creating `paper/main.tex`, check the repository status:

```shell
git status
```

Add and commit the file:

```shell
git add paper/main.tex
git diff --staged
git commit -m "Add draft LaTeX manuscript"
```

This creates a checkpoint. Later, when you edit the manuscript, git can show
exactly what changed.

For example:

```shell
git diff
```

This is much easier to review when the document is written clearly and line
breaks are not too long.

## Keep lines readable

A practical habit is to keep LaTeX source lines reasonably short. Around 80
characters is a useful guide, not a strict rule.

This is harder to review:

```latex
This sentence is very long and continues across the editor for a long time, which makes it difficult to inspect the change in git or in a pull request.
```

This is easier to review:

```latex
This sentence is easier to review because it is split across several lines in
the source file. LaTeX treats the line break as a normal space when it builds
the PDF.
```

The PDF output is the same in both cases, but the second version is easier to
edit and review.

## Add a figure

Figures should usually be generated by code and saved into a project folder
such as `figures/`.

For example, if the plotting section created:

```text
figures/tips_summary.png
```

then it can be included in the manuscript with:

```latex
\begin{figure}
  \centering
  \includegraphics[width=0.85\linewidth]{../figures/tips_summary.png}
  \caption{Relationship between bill total, tip amount, and party size.}
  \label{fig:tips-summary}
\end{figure}
```

Refer to the figure using the label:

```latex
Figure~\ref{fig:tips-summary} shows the main pattern in the data.
```

Do not write figure numbers by hand. Let LaTeX number the figures for you.

After adding the figure to the manuscript, inspect and commit the change:

```shell
git status
git diff paper/main.tex
git add paper/main.tex
git diff --staged
git commit -m "Reference generated figure in manuscript"
```

## Add a table

Tables can also be generated by code. In the publication-ready tables section,
we created:

```text
tables/tips_by_party_size.tex
```

Include it with:

```latex
\input{../tables/tips_by_party_size.tex}
```

This means the manuscript reads the generated table directly. If the analysis
changes, rerun the table script and compile the document again.

Avoid copying table values into the manuscript by hand unless there is a strong
reason to do so.

Save the manuscript change:

```shell
git status
git diff paper/main.tex
git add paper/main.tex
git diff --staged
git commit -m "Include generated table in manuscript"
```

## Add references

References should also be managed as structured data. Create:

```text
paper/references.bib
```

Add a small example entry:

```bibtex
@article{example2026,
  title = {An Example Scientific Paper},
  author = {Example, Alice and Researcher, Bob},
  journal = {Journal of Reproducible Examples},
  year = {2026}
}
```

Then update `paper/main.tex`:

```latex
Scientific workflows should make results easier to reproduce
\cite{example2026}.

\bibliographystyle{plain}
\bibliography{references}
```

If the bibliography does not appear on the first compile, run the LaTeX build
again. Bibliographies often require more than one pass. A manual build might
look like:

```shell
pdflatex main.tex
bibtex main
pdflatex main.tex
pdflatex main.tex
```

Commit the bibliography and manuscript update:

```shell
git status
git add paper/main.tex paper/references.bib
git diff --staged
git commit -m "Add manuscript references"
```

## A simple project layout

A small project might look like this:

```text
project/
+-- paper/
|   +-- main.tex
|   +-- references.bib
+-- figures/
|   +-- tips_summary.png
+-- tables/
|   +-- tips_by_party_size.tex
+-- scripts/
|   +-- plot_tips.py
|   +-- table_tips.py
```

This layout keeps the manuscript close to the outputs it uses, while still
making it clear which files are source documents and which files are generated.

## Checklist for scientific writing with LaTeX

Before sharing a draft, check:

- Is the manuscript tracked with git?
- Are generated figures stored in a predictable folder?
- Are generated tables included from files rather than copied by hand?
- Are figures and tables referenced with labels?
- Are references stored in a `.bib` file?
- Are source lines short enough to review comfortably?
- Can the document be rebuilt by someone else?

## Summary

In this section, we used LaTeX as part of a reproducible writing workflow.

We:

- created a small manuscript
- tracked it with git
- discussed why plain-text writing is useful for review
- added a figure using `\includegraphics`
- included a generated table using `\input`
- added references through a bibliography file

The main lesson is that writing is part of the research workflow. A manuscript
should not be disconnected from the code, figures, tables, and data that support
it.
